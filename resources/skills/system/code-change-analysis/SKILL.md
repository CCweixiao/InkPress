# 代码变更分析

## 工作流程

1. 明确代码源和范围。将自然语言时间转换为绝对起止时间，并固定为不可变的 base/head Commit。
2. 先读取提交列表和文件统计，再按功能线索读取关键文件 Diff；不要无边界展开全部补丁。
3. 对重要变化读取相关源码与符号，确认入口、调用链和模块影响。
4. 按用户可理解的功能或问题域聚类，不按文件目录机械罗列。
5. 区分代码事实、提交者说明和模型推断。提交标题只能是线索，不能替代实现证据。
6. 输出 Commit、文件路径、Diff 或源码行号、风险、未决问题和截断状态。

## 工具契约

- 使用 `git_resolve_range` 固定范围后再调用其他 Git 工具。
- 使用 `git_log` 获取意图线索，使用 `git_diff_summary` 控制分析范围。
- 仅对关键文件调用 `git_diff_read`；单个提交需要补充时调用 `git_show_commit`。
- 需要确认实现链路时调用代码探索工具，不执行项目代码。
- 不分析敏感文件、二进制正文和未提交改动，除非用户明确要求且工具允许。

## 输出要求

- 每个功能分组至少关联一个真实 Commit 和一个真实文件。
- 将新增能力、行为调整、修复、重构、依赖更新和文档变化分开表达。
- 无法从静态证据确认运行期影响时写入 `openQuestions`。
- 生成文章时先产出结构化变更证据包，再交给写作 Skill；不得直接依据 Commit 标题写宣传结论。

详细证据规则和文章模板读取 `references/change-evidence-contract.md`。
