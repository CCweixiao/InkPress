## 二、核心问题：为什么需要字节码保护

InkPress 的 License 拦截逻辑（`guard.ts`、`client.ts`、`trial.ts`）目前以**明文 JS** 分发在 Electron 包内。攻击者只需 patch 一行 `return null` 即可绕过所有客户端拦截。

虽然服务端 API 校验不可绕过，但本地功能（编辑器、素材浏览等）会裸奔。

**方案**：在打包流水线中将 esbuild 产出的单文件 `server.js`（~30 MB）编译为 V8 字节码 `server.jsc`，分发包内不再含可读的服务端源码。

## 三、审核重点

### 3.1 V8 版本绑定（最关键的约束）

V8 字节码绑定 V8 版本。运行时与编译时必须用同一版本的 V8，否则加载 `.jsc` 报 `ERR_INVALID_BYTECODE`。

| 环境 | V8 版本 | 用途 |
|---|---|---|
| Electron 42（`ELECTRON_RUN_AS_NODE=1`） | 14.8.x | **编译 + 运行时**（匹配） |
| 系统 Node 22 | 12.4.x | 不可用于编译 |

**审核点**：
- `compileBytecode()` 通过 `resolveElectronBinary()` 解析 Electron 二进制路径，用 `spawnSync(electronBin, [...], { env: { ELECTRON_RUN_AS_NODE: "1" } })` 启动编译
- `resolveElectronBinary()` 优先 `require("electron")`（返回二进制绝对路径），回退 `node_modules/.bin/electron`
- **绝不能**用 `process.execPath`（tsx 的 Node 22）或 `node` 直接编译

### 3.2 bytenode 1.6.0 API 适配（与计划文档的差异）

计划文档基于 bytenode 1.5.7 编写，实际安装了 1.6.0。关键差异：

| 项目 | 计划（1.5.7） | 实际（1.6.0） |
|---|---|---|
| 编译 API | `bytenode.compile({ filename, output })` | `bytenode.compileFile({ filename, output })` |
| 异步性 | 同步 | **异步**（async） |
| V8 flags | 手动或隐式 | `require('bytenode')` 自动设置 |

**审核点**：
- `compile-bytecode.cjs:39` 使用 `async` IIFE 包装 `await bytenode.compileFile(...)`
- `require('bytenode')`（`compile-bytecode.cjs:42`）在注册 `.jsc` handler 的同时设置 `--no-lazy` + `--no-flush-bytecode`（bytenode `lib/index.js:12-15`），与运行时 loader 加载 `.jsc` 时设置的 flags 一致
- 未传 `electron` / `electronMain` 标志 → 走 `compileCode`（同步、当前进程），使用当前进程的 Electron V8——避免 `electronMain` 的二次 spawn

### 3.3 薄加载器格式

`server.js` 编译后被覆写为薄加载器。必须与 bytenode 官方 `loaderCodeCommonJS` 一致：

```javascript
require('bytenode');
module.exports = require('./server.jsc');
```

**审核点**：
- `compile-bytecode.cjs:63` — 必须有 `module.exports =`，否则导出不会传播（库模块会得到 `{}`）
- 对 InkPress server.js 而言（启动脚本，无有意义导出），`module.exports =` 是冗余但安全的

### 3.4 执行顺序（prepare-standalone.ts IIFE）

```
6. bundleServerJs()          — esbuild 把 node_modules 压成单文件 server.js
7. pruneBundledNodeModules() — 删除非 externals 包
8. slimBundle()              — 删除 .ts/.map/.md 等
9. ensureBytenodeInBundle()  — 复制 bytenode 到 bundle/node_modules ← 新增
10. compileBytecode()        — server.js → server.jsc + 薄加载器      ← 新增
```

**为何 9-10 必须在 7-8 之后**：
- `pruneBundledNodeModules()` 会删除非 externals 闭包的包（bytenode 不在闭包内）
- `slimBundle()` 会删除 `.md`/`.map` 等文件
- 编译后覆写的薄加载器 `server.js` 不再被 `slimBundle` 触及

**审核点**：
- `prepare-standalone.ts:150-163` IIFE 中步骤 9-10 顺序正确
- `ensureBytenodeInBundle()` 在 `pruneBundledNodeModules` 之后执行，确保 bytenode 不被删除

### 3.5 ensureBytenodeInBundle 的体积

bytenode 是纯 JS 包（~5 KB 单文件，无 native 绑定，无 dependencies），直接 `fs.cpSync` 复制即可。

**审核点**：
- `prepare-standalone.ts:1229-1239` 用 `dereference: true` 解析 pnpm 符号链接
- 无需依赖闭包处理（bytenode 没有 dependencies）

### 3.6 失败策略

| 场景 | 行为 |
|---|---|
| 编译失败（默认） | `exit(1)` 终止构建 |
| `INKPRESS_BYTECODE_FALLBACK=1` + 编译失败 | 打印警告，回退明文 `server.js` |
| `server.jsc` 产物不存在 | 视为失败 |

**审核点**：
- `prepare-standalone.ts:1279-1290` 先检查 `result.status !== 0 || !fs.existsSync(jscPath)`，再决定回退或退出
- 回退时 `server.js` 仍是 esbuild 产出的明文（未被覆写为薄加载器）

### 3.7 SHA-256 完整性校验文件

`compile-bytecode.cjs:57-59` 计算 `server.jsc` 的 SHA-256 写入 `server.jsc.sha256`。

**注意**：当前实现**仅生成校验文件，运行时不校验**。这是为未来完整性校验预留的产物。如需启用运行时校验，需在薄加载器或 `electron/main.ts` 中增加校验逻辑。

## 五、潜在风险与回滚

### 5.1 风险点

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| Electron 版本升级后 V8 变化导致 `.jsc` 失效 | 中 | 运行时报错 | 每次 `electron:prepare` 重新编译，不跨版本复用 `.jsc` |
| bytenode 1.6.x API 再次变更 | 低 | 编译脚本失效 | 锁定 `^1.6.0`，升级时回归测试 |
| `server.js` 体积过大导致 `vm.Script` 缓存数据不完整 | 低 | 部分函数未编译 | `--no-lazy` 确保全量编译；已用 30 MB 级 bundle 验证 |

### 5.2 回滚方式

```bash
git revert dd44834
```

回滚后 `electron:prepare` 恢复为明文 `server.js`，无残留依赖（bytenode 仅 devDependencies）。
